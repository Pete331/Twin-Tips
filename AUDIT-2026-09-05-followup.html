01

What this pass found

▶

Fifteen of the twenty-three original findings are genuinely fixed, confirmed from the source and from running the code. Three are partly fixed and were described as done. Five remain open by choice. Three are new.

Read this first. Every fix checked here was written by the same author, in the session immediately before this audit. This is a self-review, which is a weaker instrument than an independent one: the blind spots that let a gap through are the same blind spots now looking for it.

That shows in what turned up. Two of the three new findings (F1 and F3) are gaps in that repair work, and neither was found by re-reading the code — both came out of running it. F3 contradicts a claim written in the source comment beside it. Treat the "fixed" column as well-evidenced, and the absence of further findings as unproven.

The three things worth acting on

New high  F1 — the late-joiner fix expires at the end of the season

C2 stopped members being scored on rounds before they joined. It works, and a scenario proves it. But joinedAtRound records a round number and no season, so the code only trusts it while season === league.createdSeason. In any later season every member silently falls back to counting from round one.

Nothing is wrong today: all four leagues were created in 2026 and 2026 is the only season being played. It fires in March 2027, without anyone touching the code.

New medium  F2 — half the hourly job was bounded, and it was the cheap half

P5 bounded calculateSeason to a four-round window. The league scoring in the same job still walks every round of every weekly league. Measured: 31 queries and 41ms for the half that was fixed, 66 queries and 212ms for the half that was not.

New low  F3 — a field computed on every page load that nothing reads

ladderProvisional is calculated, costs a query, ships in the payload, and has no consumer anywhere in the client. The comment above it says the normal path pays nothing for it. It does.

Method, and what it does not cover

  • Baseline: commit 4a9d456, the merge before the repair work began. The diff to HEAD is 36 files, +2294 / −204.
  • Verification: a probe per finding reading the current source, then scenarios exercising the behaviour against a real database. A finding is only marked fixed where both agree.
  • Data: a throwaway database seeded from nothing and dropped afterwards. The local twin-tips database was snapshotted first and is otherwise untouched except by the two idempotent scoring jobs used for timing.
  • Not covered: production was not read in this pass, so the exposure figures for F1 come from local data. No browser or device testing was done — section 7 is a code and measurement review, not a usability one. React components remain untested (T2).

To restore the local database: node scripts/audit/dbSnapshot.js load C:/dev/twin-tips-audit2-backup

03

The three new findings

▶

F1 — New high late-joiner scoring breaks in a league's second season

The fix for C2 reads a member's joinedAtRound and refuses to score them on anything earlier. The guard that decides whether to trust that number is the problem:

services/leagueStandings.js:75 
const joined =
  season === league.createdSeason && Number.isFinite(m.joinedAtRound)
    ? m.joinedAtRound
    : leagueStart;   // -Infinity in any season but the first

The membership record has no season on it. The join route writes the current round and nothing else:

routes/leagues.js:222 
joinedAtRound: state.currentRound,

So round 3 of 2026 and round 3 of 2027 are the same number, and the only way the scorer can avoid mixing them up is to ignore the field entirely outside the league's first season. Which it does — and ignoring it means everybody counts from round one.

Scenario S-02 seeds a league created in 2100, played in 2101, with a member joining at round 3. She is entered into rounds 1, 2, 3 and 4. That is the defect C2 fixed, returning with a one-season delay: pool entries she never made, buy-ins she never paid, rounds she could win without being in them.

Exposure. None yet. Every local league has createdSeason: 2026 and 2026 is the only season with tips in it. This is a dated fuse, not a live bug.

Fix. Put the season on the membership — joinedAtSeason beside joinedAtRound — and have memberFrom read the pair. Existing rows backfill to league.createdSeason, which is exactly what the current code already assumes about them.

F2 — New medium the hourly re-score is still half unbounded

P5 was recorded as fixed. calculateSeason is genuinely bounded now, with three scenarios covering the window and its two escape hatches. But the same cron also runs scoreAllWeekly, and that was never touched:

services/leagueRounds.js:103 
const done = [];
for (const round of rounds.filter((r) => r <= lastComplete)) {
  done.push(await scoreRound(league, season, round, members));
}

Every eligible round, for every weekly league, every hour. Counting the queries the driver actually issued on the local season:

31 / 41ms
calculateSeason — the half that was bounded
66 / 212ms
scoreAllWeekly — the half that was not
25 × 25
Tip.find plus bulkWrite, per hour, across 3 leagues

The unbounded half now costs five times the bounded one, and it grows with rounds times leagues rather than with rounds alone. The same window and the same never-scored rescue apply directly.

F3 — New low a query per page load for a field nobody reads

getSeasonState returns ladderProvisional. Searching the whole client for it returns nothing — its sibling ladderStale is rendered at TipsPage/index.jsx:653, and this one found no consumer. It is not free:

services/season.js:322 
// Only queried when the expected snapshot is absent, so the normal path pays
// nothing for it.
let ladderRound = haveExpectedLadder ? previousRound : null;
let ladderProvisional = false;

if (needsLadder) {
  const rows = haveExpectedLadder
    ? await db.Standing.find({ year: season, round: previousRound })
        .select("provisional")
        .limit(1)                                    // the normal path
    : await standings.getLadderForRound(season, currentRound);
  ...
}

The comment is wrong. The if (needsLadder) block runs on both branches, and the healthy branch is the Standing.find one — so the normal path pays a query, for a value that is then discarded by the client. Counted against a warm cache, a page load issues three queries and all three come from this block.

Either give it a consumer — a ladder taken from a round that had not finished is worth a line on the page, which is the argument that justified computing it — or delete the field and the query. The comment is wrong either way.

No regressions found. Every non-comment deletion in the diff accounts for itself: the two throwaway scripts, the moment imports, the four latin-ext font imports, the five synchronous bcrypt calls, and the memberIds parameter that became members so the scorer could see joinedAtRound. Nothing was quietly weakened.

Four things were checked specifically because they were the plausible places for a fix to have gone wrong:

  • Cache invalidation is complete. Both fixture writers call forgetFixtures — liveScores.js:151 and seasonSync.js:261. A cache with one writer missing would serve a stale scoreline during a game. Scenario S-11 proves both halves: the cache genuinely holds a stale read, and invalidating it genuinely clears it.
  • Dropping latin-ext stranded no character. The only non-ASCII characters anywhere in client copy are © (U+00A9) and · (U+00B7). Both sit inside the latin subset's range, so nothing falls back mid-sentence.
  • moment is genuinely gone. Not in client/package.json, not installed, and the single match for the string in the built bundle is the copy "Try again in a moment."
  • The 24-hour grace does not settle a live game. The postponed-game fix declares a round settled when its stragglers are all more than a day overdue. Scenario S-04 confirms a game that bounced an hour ago and is still being played does not trigger it.

Two deliberate synchronous bcrypt calls remain in config/passport.js. They build the absent-user hash once at module load, which is the point of them, and they are not on a request path.

This is a healthy tree. The two gaps are cosmetic:

  • mongoose 9.9.4 → 9.9.5. Query casting for nested $expr, dotted-path selection, custom cast error messages, and a TypeScript return type. Nothing security-related, nothing breaking. Worth taking, not urgent.
  • eslint 10.9.1 → 10.10.0. A development dependency that never ships.

Runtime. Node 24 is the current Active LTS line and the app declares 24.x and runs 24.19.0. Node 26 went Current in May 2026 and takes over the Active line around October, moving 24 to Maintenance. No action needed — worth knowing before planning the 2027 season.

Secrets. The local .env holds four keys — SQUIGGLE_CONTACT, MAIL_FROM, BREVO_API_KEY, ODDS_API_KEY. None carries a VITE_ prefix, so none can reach the browser bundle, and no production database URI is present locally.

06

Scenarios

▶

Fifteen scenarios run against a real database, seeded from nothing and dropped afterwards. Each states what it expects before it runs, so a pass means the expectation was met rather than that nothing threw.

The single failure is F1. Six scenarios failed on the first run for a reason worth recording: the harness could not seed a User without firstName, lastName and favTeam, because that schema declares them required. Seeding a Tip never failed, because that schema declares nothing required at all. That contrast is finding D3, demonstrated by accident.

P1 did what it set out to do: the fixture read that dominated the page load is off almost every request, and the time-dependent decisions are still recomputed against the clock on every call, so lockout is never late. What is left is the ladder block, and a third of it exists for a field the client discards.

Indexes are declared and built

Declaring an index in a schema is not the same as having one. Both new indexes exist on the local database and the queries that were collection scans now use them:

  • tips.season_1_round_1 — Tip.find({season, round}) examines 6 documents to return 6. The never-scored lookup examines 126 to return 0, which is the index doing its job on a negative match.
  • teams.id_1 — Team.findOne({id}) examines exactly 1.

Every hot read on tips and fixtures is now an index scan. None was before.

Testing

281 tests, all passing, covering scoring, routes, sessions, the sync, and four client utility modules. The gap named in T2 is unchanged: there are no component tests, and the four client test files are all pure functions. The React components have never been exercised by anything but a person clicking on them.
